**同时发现并修复了 1 个真实缺陷**：

| 项目 | 内容 |
| --- | --- |
| 现象 | 去重报告统计出 **42 组**重复（跨类 40 + 类内 2），而实际只有 **22 组**（跨类 20 + 类内 2） |
| 根因 | `deduplicate()` 中 `report.append(...)` 被误写进内层循环，导致每个跨类组被**重复记录 2 次** |
| 影响面 | **仅影响报告的行数统计**；被删除的样本数（42 张）、保留样本数（2990 张）与每类张数**均正确** |
| 修复 | 将 `report.append(...)` 移出内层循环 |
| 复验 | 修复后组数 = 22（跨类 20 + 类内 2），与审计结果一致；去重结果与修复前完全相同 |

> **这件事本身值得记下来**：缺陷是**被"与预测值逐项比对"这一步抓出来的**，
> 而不是靠肉眼读代码。如果当初只是"跑通了就算过"，
> 这个错误的组数就会原样写进报告——正对应 **G5** 存在的意义。
>
> 同时也说明：**G5 不只是"数字由脚本生成"，还要求数字经得起与独立来源的比对。**
> 本例中"独立来源"就是上一阶段手工审计得到的 22 组。

### 2.4 冒烟测试（2026-10-08）

**目的**：正式训练前验证「数据读取 / 模型维度 / 反向传播 / 产物落盘」四项。
**配置**：`configs/smoke_test.yaml`（每类 10 张、2 轮、batch=4）。

#### 第一次运行：EXIT=0，但**暴露 2 个缺陷**

| # | 缺陷 | 现象 | 根因 | 影响面 |
| --- | --- | --- | --- | --- |
| 1 | 控制台编码 | `UnicodeEncodeError: 'gbk' codec can't encode character`，输出被 `--- Logging error ---` 打断 | Windows 控制台默认 GBK；日志文件是 UTF-8（正常），但 StreamHandler 写控制台时崩溃 | **仅影响控制台显示**；`train.log` 完整。但会打断输出、掩盖真实信息 |
| 2 | **自检误判** | `④ 自检结论: ❌ 未通过`，而模型输出 `(4, 6)` 其实**是对的** | `sanity_check()` 用「当前 batch 内出现过的标签种类数」当期望类别数；batch=4 且标签为 `[2,3,4]` 时算出 3 ≠ 6 | **误报**。若不去深究，会被误认为模型有问题 |

### 2.7 正式训练前发现的缺陷与守卫实测（2026-10-08）

#### 缺陷 4：`num_workers > 0` 时 DataLoader 直接崩溃

| 项目 | 内容 |
| --- | --- |
| 现象 | `OverflowError: Caught OverflowError in DataLoader worker process 0.` → `Python int too large to convert to C long` |
| 根因 | `seed_worker()` 用的 `% 2**32` 会产生 ≥ 2³¹ 的种子；**Windows 上 C 的 `long` 是 32 位**，`np.random.seed()` 装不下 |
| **为什么冒烟测试没发现** | 冒烟配置是 `num_workers: 0`，`seed_worker` **根本不会被调用**；正式配置用了 `num_workers: 2` 才暴露 |
| 修复 | 改为 `% 2**31`（PyTorch 官方示例的 `% 2**32` 在 Windows 上必然踩这个坑） |
| 影响约束 | **G5** |

> **教训**：**冒烟测试的配置必须尽量贴近正式配置。**
> 这次两者只差一个 `num_workers`，就漏掉了一个"正式训练必然崩溃"的缺陷——
> 如果跳过验证直接开正式训练，会在第 0 步就失败。

#### G6 守卫实测：冒烟结果进不了正式汇总

```
$ python src/summarize.py --runs <冒烟运行1> <冒烟运行2> --name _guard_test
AssertionError: ❌ 汇总中混入了**冒烟测试**运行！冒烟结果不得作为正式结论（G6）。
   冒烟运行: ['smoke_small_cnn_seed42_20261008-183023', 'smoke_small_cnn_seed42_20261008-185331']
```

`src/summarize.py` 在汇总前会检查每个运行的 `is_smoke` 标记，
**冒烟结果永远无法进入正式汇总**。这条守卫是用"故意把冒烟运行拿去汇总"的方式实测的。

同理，`summarize.py` 还会**校验所有运行是否共用同一份数据划分**（比较 `split_index.csv` 的 MD5）：

```
✅ 全部一致 —— 所有运行共用同一份划分，可以汇总比较
```

若不一致会直接抛错并列出不同的哈希——**防止把"各自重新划分"的模型拿来比较**（G3）。

### 2.9 ⚠️ 最重要的一条：我自己提出的"背景消融"被证明是**被混淆的**

**背景**：`experiment-plan.md` 的假设 H3 是"模型会部分依赖背景"，


我当时的判定逻辑写的是 **"模型确实依赖背景纹理（假设 H3 成立）"**。

**但我停下来验证了一步**：0.1704 恰好 = 76/446，正好是测试集里 **ARJ21 的样本数**
——说明模型退化成了"恒定预测 ARJ21"。这太极端了，于是我去量化飞机在图像里到底占多大：

| 检查项 | 实测 |
| --- | --- |

### 2.10 ResNet18 迁移学习的设计决策（2026-10-09）

用户要求"说明冻结哪些层、解冻哪些层"，且只跑**一个** ResNet18 配置。
因此把原方案的 M2(frozen) / M3(finetune) **合并**为一个 `partial` 配置：

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 预训练权重 | `torchvision` 官方 `IMAGENET1K_V1`（ImageNet-1k，44.7 MB） | 可追溯；已在 `resnet18_transfer.py` 顶部注明来源、URL 与论文 |
| 分类层 | `Linear(512 → 6)`，`std=0.01` 小初始化 | 新随机初始化的层，初期输出不能过大以免冲垮预训练特征 |
| **冻结** | `conv1 / bn1 / layer1 / layer2` | 浅层 = 通用低层特征（边缘/角点），SAR 同样适用 |
| **解冻** | `layer3 / layer4 / fc` | 深层 = 任务相关语义，ImageNet 与 SAR 差异最大，最需重学 |
| 学习率 | head `1e-3` / backbone `1e-4` | 分层学习率（discriminative fine-tuning）：预训练权重用 1/10 的 lr |
| 灰度处理 | **复制成 3 通道** | 不改动任何预训练权重，是"最纯粹的迁移"；备选"改第一层"会引入人工平均 |
| 归一化 | **沿用基线的 `train_stats`** | **受控对比**：预处理若不同，差异就无法归因于模型 |

**受控对比的落实**：写了脚本逐项比对两个配置（合并 `_base_` 之后），
12 项控制变量（去重策略 / 划分种子 / 分层容差 / 输入尺寸 / 归一化 / 增强 /
轮数 / batch / 优化器 / 种子 / 早停 / max_per_class）**全部一致**，
差异只存在于模型本身的学习率设置。

> **教训（缺陷⑧）**：`resnet18_transfer.py` 独立运行时又踩了 PIL 导入顺序的坑
> （README 5.4 坑 3）——`torchvision` 先于 PIL 导入会导致 `_imaging` DLL 加载失败。
> 已在文件最顶部固定 PIL 导入并加注释。
> **同一个环境的坑会重复出现**，所以把它写进 README 是值得的。

### 2.12 错误分析与可解释性分析（2026-10-09）

**最终模型**：`resnet18_seed123`（按**验证集** macro-F1 = 0.9215 选出；
模型族比较：resnet18 `0.9199±0.0011` vs cnn_baseline `0.6802±0.0118`）。
`final_model_selection.json` 中明确记录 `test_set_used_for_selection: false`。

**错误分析**：测试集 446 张，错分 **36 张（8.07%）**。
错分最集中的方向：

| 真实 → 预测 | 数量 | 占错分 |
| --- | ---: | ---: |
| **A220 → A320321** | 11 | 30.6% |
| **A320321 → A220** | 8 | 22.2% |
| 其余 11 个方向 | 共 17 | 47.2% |

→ **A220 ↔ A320321 一对就占了全部错误的 52.8%**。

**为什么容易混（用数据回答，不是猜）**：

| 统计量 | A220 | A320321 | 相对差异 |
| --- | ---: | ---: | ---: |
| 原图宽（中位） | 82.0 | 92.0 | 11.5% |
| 原图高（中位） | 72.0 | 78.0 | 8.0% |
| 长宽比 | 1.137 | 1.238 | 8.5% |
| 亮目标面积占比 | 0.724 | 0.832 | 13.8% |
| 平均亮度 | 17.43 | 14.76 | 16.6% |

**所有统计量相对差都 < 20%** → 两类在尺寸/外形上**高度接近**，
且**双向互错**（不是单向），说明特征分布在决策边界附近交叠。

**⚠️ Grad-CAM 环节的一个重要方法学发现**：

第一次算出来的定位指标只有 **1.10×**（几乎等于随机），差点据此写下
"模型不看目标"。停下来诊断后发现：**ResNet18 在 96×96 输入下下采样 32 倍，
`layer4` 只有 3×3**（每格 = 原图 32×32 像素）——**是 CAM 太粗，不是模型没看**。

改做**跨层对照**后：

| 目标层 | CAM 网格 | 落在亮像素上 | 随机基线 | 提升 |
| --- | --- | ---: | ---: | ---: |
| `layer3` | **6×6** | 0.0878 | 0.0653 | **1.34×** |
| `layer4` | 3×3 | 0.0774 | 0.0653 | 1.18× |

**最终结论仍保持克制**：只有 **1.34×**，属于"**有聚焦倾向但不强**"，
并明确写出三条方法学局限（目标用亮像素近似而非标注框；飞机占画面 3/4 导致
指标分辨力天生有限；`layer4` 分辨率不足）。
**没有写成"模型主要看飞机主体"。**

> **这是本项目第二次在"写结论之前先检验数字"上救回一个错误结论**
> （第一次是背景消融被混淆）。
> **同一个模式反复出现**：数值看起来支持某个结论时，
> 先问一句"这个数值的构造方式，会不会让另一个解释也成立？"
